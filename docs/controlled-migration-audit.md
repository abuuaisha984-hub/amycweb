# Controlled database and storage migration audit

Read-only audit performed before migration implementation on 2026-10-08.

## Findings

- **Database:** The checked-in application schema and all 15 existing Prisma migrations use SQLite. `DATABASE_URL` points to a local SQLite file in `.env.example`. `src/lib/db.ts` forces local development onto that SQLite database and caches a Prisma Client singleton.
- **PostgreSQL compatibility:** The schema uses portable scalar fields, string-encoded JSON, cuid string IDs, `DateTime`, booleans, relations, indexes and unique constraints. No SQLite-only Prisma types or raw SQL were found in application code. The existing migration SQL is SQLite-specific and cannot serve as PostgreSQL migrations. `scripts/sync-postgres-schema.mjs` currently copies the schema and changes only its provider; there is no PostgreSQL migration history or data transfer process in the repository.
- **Models:** The schema includes users and audit logs; categories, articles, events, schools, regions, leaders, programmes, galleries and gallery items; documents and messages; settings and visitor analytics/events. Existing relation, nullable-field, index and unique definitions need preservation in a PostgreSQL baseline.
- **Uploads:** Image uploads are written to `public/uploads/images/{regions,leaders,schools,events,media,news,programmes}` by `src/app/api/admin/images/route.ts`. Documents are written to `public/uploads/docs` by `src/app/api/admin/documents/route.ts`. `src/lib/upload-storage.ts` has a Supabase REST upload helper, but the two upload APIs do not use it; document deletion also needs inspection/update for object storage.
- **Stored file references:** Database fields include article `featuredImage`, event/region/leader/programme image fields, school `image`/`logo`, gallery item image references and document `filePath` (plus generated `fileName`). These currently use `/uploads/...` paths. Existing uploaded files need inventory and a verified copy before switching references or storage.
- **Upload security:** The image API checks session, role permission, size, extension/MIME and file signature, then normalizes with Sharp and uses a random filename. The document API checks session, permission, size, MIME and file signature and uses a random filename. Existing smoke scripts cover authentication, image signatures and size limits; the current local-filesystem assertions will need updating when object storage is wired in.
- **Environment/configuration:** `.env.example` currently documents SQLite, NextAuth, visitor analytics and initial admin seed variables. The partial storage helper expects `SUPABASE_URL` or `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and optional `SUPABASE_STORAGE_BUCKET`; current deployment docs describe a persistent VM/SQLite setup. `netlify.toml` and a `build:netlify` script are already present in the dirty worktree.
- **Git/data safety:** `.gitignore` now excludes env files, database files, backups and uploads. The index shows `.env` and `db/custom.db` staged for deletion, while a local `db/custom.db` and `db/backups` directory exist; neither was opened, copied, or changed. A pre-existing secret-cleanup report records historical exposure, including a plaintext initial admin credential in an older seed revision, and says no remote is configured. No history rewrite or credential values were inspected.
- **Existing migration work:** The worktree already has extensive staged, unstaged and untracked changes across application, deployment, schema and tests. Preserve all of it; do not reset or clean the checkout. The current netlify build generates a provider-transformed Prisma schema, while the normal schema and migration lock remain SQLite.
- **Migration risks:** PostgreSQL requires its own migration baseline/history and explicit SQLite-to-PostgreSQL export/import. File URLs must be migrated/copied consistently with records. Production database/storage credentials must be configured outside Git. The committed SQLite file and Git history contain sensitive data; keep the original DB untouched and use an isolated staging target before any production cutover.

## Current status

The audit dry run read the local SQLite database without exporting row contents or changing it. It found 21 application tables and 1,361 records: User 6, AuditLog 207, Category 17, Article 12, Event 5, School 31, Region 25, Programme 9, Project 0, Document 18, MediaItem 0, Gallery 1, GalleryItem 1, Page 5, Leader 24, ContactMessage 2, VisitEvent 957, Visitor 15, SiteSetting 14, SocialLink 8, ExternalLink 4. These are counts only; test/demo status has not been classified.

No records or upload files have been migrated. A PostgreSQL baseline and guarded staging importer have been added. The verified SQLite backup dry run returned the same 1,361 records across 21 tables. The upload migration dry run found 43 local objects (38 WebP images, 4 PDFs, 1 DOCX). No PostgreSQL staging database or Supabase project was configured, so database import, object upload/delete, persistence, analytics integration, and production CRUD remain unverified. The local database and upload files remain untouched.

The Netlify build and normal standalone build pass. Lint, TypeScript, Prisma schema validation (with a PostgreSQL-shaped placeholder URL), upload security smoke, regional authorization smoke, and backup restore verification pass. The analytics smoke test was not run because the existing script targets port 3000 and directly writes to the configured SQLite database; it needs an isolated runtime fixture first.
